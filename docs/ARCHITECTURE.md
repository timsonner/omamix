# Architecture

Scaffold decisions for omamix. The product requirements are in [SPEC.md](SPEC.md). The laptop measurement those decisions used is in [AUDIO-BASELINE.md](AUDIO-BASELINE.md).

## UI: egui / eframe

**Choice: egui 0.36 with eframe**, `crates/omamix`.

| Toolkit | Fit for this mixer |
| --- | --- |
| egui / eframe | Immediate-mode painting is the meter, waveform, and spectrum path. A fader is custom code. The wheel reads raw `MouseWheel` events and steps 0.5 dB per notch only while that fader is hovered and focused. eframe's default backend is winit + wgpu with Wayland enabled, which matches Hyprland. egui 0.36 has no `raw_scroll_delta`. |
| iced | A canvas widget can draw meters, and winit talks to Wayland, but a dense strip layout is a custom widget either way, with more architecture around each control. |
| gtk4-rs / libadwaita | gtk4 4.22.4 and libadwaita 1.9.3 are installed here, so this was a real option. `GtkScale` changes value when the wheel hovers it, which is the behavior the spec forbids, and live meters mean a custom snapshot widget plus a GTK main loop beside the PipeWire thread loop. libadwaita styling follows GNOME. |

Omarchy theme colors can be a palette table later. That is not in the scaffold.

The shell draws one placeholder strip. The wheel handler reads raw `MouseWheel` events (`input.raw.events`). Positive Y is wheel-up and raises the fader. A mouse notch is one `Line` and one step of 0.5 dB (`WHEEL_STEP_DB`). Trackpad `Point` events accumulate, and a step happens only when they reach 40 points (`POINTS_PER_NOTCH`, egui's native line scroll speed), so a swipe is not one notch per event. `apply_wheel` runs only when that fader is hovered and focused. A fader that still has focus from an earlier click does not move if the pointer is elsewhere. A click that only focuses the fader does not change its value (`PointerGesture::FocusClick`). Drag still moves the fader under the pointer. One notch below −60 dB is −∞. NaN dB becomes mute and +∞ clamps to the fader's max boost before it can become a gain. The GUI was not launched in the scaffold run.

## Graph and I/O: pipewire-rs

**Choice: the `pipewire` crate 0.10.1 (pipewire-rs), feature `v1_2_0`, behind `--features pipewire`.** That feature needs **libpipewire >= 1.2**. On libspa 1.0.x the same crate fails to compile with E0425 because `spa_meta_sync_timeline` is missing. `build.rs` runs `pkg-config --atleast-version=1.2 libpipewire-0.3` (honoring `$PKG_CONFIG`). Cargo runs that script in parallel with pipewire-rs, so a normal build prints this check. A `-j1` build can still show the libspa E0425 first. Ubuntu 24.04's apt package is libpipewire 1.0.5, which is too old. The app owns its nodes. DSP runs in-process behind [`DspStage`](../crates/omamix-core/src/dsp.rs).

### Why an app-owned filter, not module-remap-source or filter-chain

UNVERIFIED: Tim reported that gpu-screen-recorder recorded silence when the default source was a pactl `module-remap-source`, and that naming the source explicitly worked. That module is a server-side Pulse compatibility node. It stays loaded until something unloads it, which fights the "pw-dump diff clean on quit" requirement, including on a crash. This session did not re-test gpu-screen-recorder.

The audio graph is one `pw_filter` (`ClockPlan::SingleFilter`) with one `process` callback, plus one adapter node in front of it. The public node is Mix Mic: `core.create_object` of the `adapter` factory with `factory.name` `support.null-audio-sink`. `mix_mic_properties()` is that node's bag (`media.class` `Audio/Source/Virtual`, `node.name` `omamix.mix-mic`). `factory.name` is set at creation and is not part of the contract bag. The filter is a separate node, `filter_properties()`: `node.name` `omamix.mix-engine`, `media.class` `Audio/DSP`. It is not an `Audio/Source`, `Audio/Source/Virtual`, `Audio/Duplex`, or `Stream/Output/Audio`, so it is not a default-source candidate and it is not tapped as desktop audio. Strip taps are input ports on the filter (`in-<peer>-FL` / `in-<peer>-FR`), linked from the peer's output ports. The filter's `capture_FL` / `capture_FR` outputs link into the adapter's input ports. A capture of Mix Mic pulls the adapter, which pulls the filter. pipewire-rs 0.10 has no `pw_filter` wrapper; `crates/omamix-pw/src/filter.rs` calls the C API. The filter flag is `PW_FILTER_FLAG_RT_PROCESS` only. `PW_FILTER_FLAG_DRIVER` is not set. PipeWire then marks the filter `node.want-driver` and points `node.driver-id` at Mix Mic. The `support.null-audio-sink` factory marks the adapter `node.driver`. A capture of Mix Mic clocks the adapter, which clocks the filter. Neither property bag writes `node.driver` or `node.want-driver`. Output ports are `format.dsp` `32 bit float mono audio`, with `PW_FILTER_PORT_FLAG_MAP_BUFFERS`.

Mix Mic properties:

- `media.class` = `Audio/Source/Virtual`
- `node.name` = `omamix.mix-mic`
- `node.description` = `Mix Mic`
- `node.virtual` = `true`
- `media.role` = `Production`
- `audio.channels` = `2`, `audio.position` = `FL,FR`
- `priority.session` = `1` and `priority.driver` = `1`
- `node.latency` is omitted. PipeWire keeps the graph rate and quantum. The limiter delay is `ProcessLatency` in samples at that rate.
- `node.dont-reconnect` = `true` and `node.autoconnect` = `false`
- `object.linger` = `false`
- `omamix.owned` = `true`
- `adapter.auto-port-config` and `node.param.PortConfig` create the stereo dsp input ports and the monitor outputs on this node. The format is F32P, two channels, FL and FR, and it does not set a sample rate. A session manager is not required for those ports. A recorder still needs a link to `capture_FL` / `capture_FR`. WirePlumber makes that link when it is present.
- `node.param.Props` starts at unity: volume 1.0, mute false, `channelVolumes` `[1.0, 1.0]`. That is 0 dB, not a microphone level. The user sets each input.

WirePlumber ranks a default-source candidate by `priority.session`, then `priority.driver`, otherwise 0. The best candidate wins. There is no fallback source at another priority (UNVERIFIED this round: the earlier read of WirePlumber 0.5.17 `rescan.lua`, `find-best-default-node.lua`, and `wireplumber.conf` was not repeated). Priority 1 loses to any higher candidate. If Mix Mic is the only `Audio/Source`, `Audio/Source/Virtual`, or `Audio/Duplex`, it becomes the default source. omamix then destroys the Mix Mic node. A stored choice does the same thing at startup: when `default.audio.source` is already `omamix.mix-mic`, the warning is logged and the node is removed right away, before it is left published. Pick another source, then start omamix again. Removing it leaves WirePlumber's runtime `default.audio.source`. `default.configured.*` is never written. The unplug check is `scripts/unplug-watch.sh`, not a unit test. `priority.driver` is 1 on Mix Mic and on the filter, so Mix Mic loses a driver election against an ALSA device. The adapter still carries `node.driver` from the null-audio-sink factory, which is how a capture of Mix Mic gets a clock. The filter is the follower (`node.want-driver`, `node.driver-id` equal to the Mix Mic node). `node.dont-reconnect` and `node.autoconnect=false` tell the session manager not to rebind the node or to pull existing clients onto it.

omamix binds the PipeWire metadata object named `default` and listens to `property` events for `default.audio.source` and `default.audio.sink`. It never calls `set_property`. `allow_metadata_write` is a trimmed, case-insensitive allow list, and that list is empty, so every metadata write is refused. Mix Mic is created only after `default.audio.source` has been read. If that key never arrives, Mix Mic is not published. The first read is not logged as a change. A later change is logged. If the default source name is `omamix.mix-mic`, omamix logs a warning and destroys the Mix Mic node. That includes the first read, so a stored choice of Mix Mic tears the node down as soon as omamix starts. The session default stays where the session manager left it. The Mix Mic id and the filter id are accepted only when the node has `omamix.owned`, this process's `client.id`, and the matching `node.name`. A foreign node that reuses either name does not replace the id from `pw_filter_get_node_id`.

A source scan in the `metadata` tests reads `crates/`, `scripts/` except the exact paths `scripts/prove.sh` and `scripts/rate-matrix.sh`, and `PKGBUILD`. A different file named `prove.sh` stays in the scan. `scripts/prove.sh` is the private-socket procedure: it links and it writes the private default, and a separate test checks that it does not set a login default, a volume, or a mute. `scripts/rate-matrix.sh` is the private rate and quantum procedure. The same scan skips that exact path, and the same test checks that it does not set a login default, a volume, or a mute. It flags a fixed list: default-device write spellings, the metadata, link, and `pw-cli` command names, `systemctl`, `amixer`, `alsactl`, joined config-directory paths, a `.join` of `wireplumber`, `pipewire`, or `hypr` with or without space after the parenthesis, the method form `path.push` and the UFCS forms `PathBuf::push` and `Path::join`, a raw string of those directory names, a one-letter const or let passed to `.join`, and a const passed to `.push`, `set_param` and `set_property` in every file, `Command` aliases including `<Command>::new`, `concat!` and slice `.join` strings that assemble those tokens, `format!` the same way, `libc::system`, `libc::fork`, `libc::vfork`, `nix::unistd::fork`, `execv`, `execvp`, and `posix_spawn`. `build.rs` may spawn only `pkg-config`. The scan does not prove that every shell-out is absent, and it does not prove that every split string outside those patterns is caught.

Mix Mic's filter connects with a SPA Props pod: `channelVolumes` `[1.0, 1.0]`, `mute` false, and the matching soft-volume fields. The public adapter carries the same unity values in `node.param.Props`. `process` writes the samples itself and does not multiply by the filter pod. `--tone` adds a 440 Hz sine at amplitude 0.2 on Mix Mic only, for a recorder aimed at that node. That amplitude is the test tone, not a microphone gain.

Headphone sends and the monitor of the final mix are separate `Stream/Output/Audio` streams on the same client. They are not a second mixer and they are not the filter. The filter `process` writes the master quantum into a seqlock (`MixSlot`). The monitor stream's `process` only copies that slot. A headphone send must copy that strip's tap, not the master mix, because the master includes the mic. `--monitor-mix` creates the monitor stream. Headphone streams are not created yet: there is no per-strip slot, and copying `MixSlot` into headphones would play the mic. Both property bags set `node.autoconnect=false`, `node.dont-reconnect=true`, `object.linger=false`, and `omamix.owned=true`, and neither sets `target.object` or `PW_STREAM_FLAG_AUTOCONNECT`, so they do not attach to a sink. They can run on the sink's driver and may repeat or skip a quantum relative to the filter.

Easy Effects, while it was still installed, published its virtual mic as `media.class = Audio/Source/Virtual` with `factory.name = support.null-audio-sink` (`easyeffects_source`). A bare `pw_filter` exposes `format.dsp` ports. WirePlumber does not register that as a Pulse source (`no usable format found`), so `pactl list sources` omits it and a recorder's `--target` falls back to the default source. The adapter node is what shows up in source pickers. It is still not `module-remap-source`. The gsr test in [TESTING.md](TESTING.md) is what decides.

Teardown runs on the loop thread before `mainloop.quit()` returns and the thread drops the core: link proxies, the monitor stream, registry bindings, then the filter (`pw_filter_disconnect`, remove the hook, `pw_filter_destroy`). `object.linger=false` is on the filter, the monitor, and every link. Dropping the core disconnects the client, which removes what that client created. SIGINT and SIGTERM only set an atomic; the control thread then sends `Shutdown` on the PipeWire channel. `process()` catches panics so they do not unwind across the C callback. A hard kill still depends on `object.linger=false` and the client disconnecting when the process dies. A window built with `--features pipewire` opens that client and publishes Mix Mic until the window closes. A window without the feature keeps `NullEngine` and does not publish Mix Mic. `omamix --headless` without `--mix-mic` does not open a client either. Unit tests do not call `run_headless`.

### Per-app capture and re-attach

Playback apps show up as `Stream/Output/Audio` nodes. Node ids change every time the app starts. A strip stores a `RouteKey` of `application.name`, `application.process.binary`, and `media.name` when a tab or window needs to stay distinct. Those three are the re-attach key: a restarted app has a new pid and a new object serial and still matches (`RouteKey::matches_stream`). Pid and object serial are not required for that match. They only separate two streams that are live together (`disambiguates_live`). A node global does include `client.id`, `object.serial`, `node.name`, and `media.class`. It does not include `application.process.binary`, `media.name`, `application.process.id`, or `omamix.owned`. The backend binds the node for those. Whether a node is ours is our `client.id`: the client is created with `application.name=omamix`, `application.process.binary=omamix`, and `omamix.instance=<pid>-<nanos>`, and the Client global whose instance matches is ours, recorded once. `omamix.instance` can be copied onto another client. `omamix.owned` is still what keeps our nodes out of the mix, together with our `client.id` and pid. A node info event does not overwrite that client id. On `global_remove` the strip stays and the link attempt is dropped (`LinkPhase::PeerVanished`); a later global starts a new attempt.

The tap is an input port on the Mix Mic filter, not a second `pw_stream` (a stream would be a second clock). `app_capture_properties` still records the contract that must not be used to steal playback: `media.class` `Stream/Input/Audio`, `node.passive`, `node.autoconnect=false`, `node.dont-reconnect`, `stream.dont-remix`, `object.linger=false`, `omamix.owned`, and no `target.object` or `stream.capture.sink`. `target.object` on a capture stream is how WirePlumber steals a playback app off the user's sink. The link is additive: the app keeps its link to the sink, and the filter listens as well.

The optional "all other desktop audio" strip attaches each remaining playback stream with that same per-stream tap (`Scene::other_desktop_streams`). It does not set `stream.capture.sink` or `target.object`, so it does not monitor the sink. A stream that already has an `Application` strip is left out of "other", which keeps it from being mixed twice. `feeds_mix_mic` refuses a stream unless `media.class` is `Stream/Output/Audio`. An empty class fails closed, so `Stream/Input/Audio` capture nodes stay out. It also refuses `omamix.owned`, our `client.id` or pid, and any node [`upstream_includes_mix_mic`](../crates/omamix-core/src/route.rs) can reach from Mix Mic, including through intermediate nodes. The walk is per node. The automatic strip and an application strip with an empty `media.name` also refuse every stream of a client that captures Mix Mic, including a playback node with no PipeWire edge of its own. An application strip whose route key includes `media.name` stays on the per-node walk, so one named tab can stay a strip while another tab of the same client captures Mix Mic. A missing `node_id` fails closed when a graph is present. `application.process.binary` is read from the client object when the node omits it. On every link-added event the loop walks again and drops a tap whose upstream now includes Mix Mic, and it removes that tap's filter ports. Headphone sends and the monitor share our client, so they stay out of Mix Mic. `owned_output_feeds_mix_mic` reads the property bag and is false while `omamix.owned=true` is in that bag.

Capture devices are stored by `node.name`, which is stable across reboots for ALSA nodes. The name is whatever that machine enumerates. The app does not assume a particular device.

### DSP

v1 effects, in order: noise reduction, high-pass, 10-band graphic EQ, compressor, limiter. The master adds EQ, compressor, and a limiter that defaults on at −1 dBTP. Input trim (±24 dB) and the fader sit outside that list.

**Choice: an in-process `DspChain` of `DspStage`s.** The scaffold's strip template is five identity stages in that order, plus a real `GainStage` so tests can see enabled stages run and disabled stages get skipped. Strip pan is a balance law: left `min(1, 1 - pan)`, right `min(1, 1 + pan)`. Center is gain 1 on both channels, and neither side goes above 1. `constant_power_gains` is an equal-power formula the mix does not call (center about −3 dB per side, `L^2 + R^2 = 1`). A mono source is copied onto the stereo tap and uses the balance law, so center stays at unity. The formula stays for a later mono strip that does not exist yet. Do not wire it to a stereo strip.

Per-strip trim, fader, pan, mute, solo, and enable are atomics in `StripParamBank` (`crates/omamix-core/src/params.rs`). The control thread stores them. `StripMixer::process` loads each atomic once per block and smooths per sample. It does not lock, allocate, or take the command channel. The smoother is a one-pole with a 10 ms time constant, `1 - exp(-1 / (0.010 * sample_rate))`, so 44.1 kHz and 48 kHz share the same seconds. Gain (trim times fader, gated by mute, solo, and enable) is linear amplitude. Pan is smoothed as a position, then the balance law runs. Once that pan value has settled, the law is not recomputed. Solo matches `Strip::audible`: a solo on an enabled strip mutes the strips that are not soloed, and mute still silences a soloed strip. A disabled strip is silent, so its solo flag is ignored and does not silence the others. Enable false sets that strip's gain target to 0. Defaults are trim 0 dB, fader 0 dB, pan center (unity on both channels), not muted, not soloed, enabled. A default strip passes a finite stereo block through unchanged. The sum starts at +0.0, so a −0.0 input sample comes back as +0.0. The values match and the sign bit of a zero does not. That difference is inaudible. Those defaults are not a microphone level. The master fader in `AtomicParams` is still applied after the strip sum. Claiming a tap slot resets that slot's strip params to these defaults and its meter to silence, and freeing the slot does the same.

Per-strip meters and the master meter publish the peak and the RMS of each block, in dBFS, as one atomic snapshot. Peak is the largest absolute sample on either channel. RMS is the root-mean-square of the louder channel, so a silent side does not pull the reading down. The sum of squares is f64, so a block of samples around 1e19 does not overflow into silence. A sine whose peak is −20 dBFS reads −20 dB peak and about −23 dB RMS (−20 minus 10 log10(2)), within 0.1 dB. The strip meter is that strip's post-fader contribution. The master meter is the mix after the master fader, including the test tone when it is on. `process` stores the pair and does not hold or decay it. Meters start at silence (−∞ dB), not at 0 dBFS. A block above +24 dB is published at that ceiling, the same cap as a gain. Hold and decay are `MeterDisplay` for the UI: the peak snaps up, stays for 1 s, then falls at 20 dB/s, and it does not fall below the current block. RMS on that display is the latest block. A later meter bar treats about −60 dBFS as its floor and draws an empty bar below it. That floor is a display choice, not a measured noise floor, and the callback does not clamp to it. Those times and that floor are display constants, not a measurement of a hardware meter.

Each strip and the master keep a fixed SPSC ring of those post-fader stereo frames (one producer and one consumer, 4096 frames). `process` pushes and drops whatever does not fit, and an atomic counts those dropped frames. It does not block or allocate. A stalled reader keeps the frames it has not popped. The same rings are what a later spectrum and loudness meter will read, off the audio thread. Claiming or freeing a tap slot asks that reader to drop the strip's unread frames on its next pop. The 38 strip rings are about 1.2 MB.

The high-pass and the 10-band graphic EQ run in `StripMixer::process` on each strip's input, before the trim and fader gain, and again on the master sum before the master fader. Centers are the ISO 266 octave bands from 31.5 Hz to 16 kHz. Each band is an RBJ peaking section, not a low shelf and not a high shelf, with a bandwidth of one octave, clamped to +/-12 dB. The 8 kHz and 16 kHz bells use the RBJ bilinear bandwidth warp, so the skirts are not symmetric in hertz. At 44.1 kHz the upper half-octave of the 16 kHz band is past Nyquist. Center gain is still the cookbook value. A center at or above 0.99 times Nyquist is disabled (identity), and `EqSettings::band_disabled` reports that. At 32 kHz the 16 kHz band is disabled. The high-pass is an RBJ biquad with Butterworth Q. When it is enabled and no other cutoff was set, the cutoff is 80 Hz. 80 Hz is a generic default, not a measured microphone or a measured room. Both start off: every band at 0 dB and the high-pass disabled, which is a flat bypass, so a default strip still passes a finite block through unchanged. Coefficients are computed in f64 and stored in f64, because an f32 pole at 31.5 Hz drifts at 192 kHz. `EqWriter` is the only producer. It is not `Clone` and not `Sync`. `EqReader` holds the consumer index, one per channel. It is not `Clone` and not `Sync`, and `StripMixer::process` takes `&mut EqReader`, so two mixers cannot share one reader. The loop thread builds coefficients and publishes the whole block by swapping an index in a triple buffer. `process` holds that reader and only loads the block. It does not build coefficients, allocate, or lock. A new block is linearly ramped across 256 samples, not across a short quantum, and the last sample of that ramp uses the new coefficients. A section that becomes identity clears its delay line, so turning it back on does not click while other sections still run. `response_db` is the pure magnitude of a setting, for the EQ widget. A sine sweep in the unit test `sine_sweep_matches_response_db_within_half_a_decibel` stays within 0.5 dB of it, including 31.5 Hz at +12 dB at 192 kHz (`low_band_at_192k_stays_within_half_a_decibel`). The compressor runs in `StripMixer::process` after the graphic EQ and before the trim and fader, and again on the master after the master EQ and before the master fader. It is a stereo-linked feed-forward peak compressor. The detector is a one-pole with separate attack and release time constants, `1 - exp(-1 / (seconds * sample_rate))`. The static curve is `static_reduction_db`: a hard knee, or a soft knee of a given width. Defaults are bypassed, so a default strip does not change samples. The follower stays live while the stage is bypassed, so turning it on does not start from a stale envelope. A bypassed sample is returned unchanged. The numbers behind that switch are generic: threshold -18 dB, ratio 4:1, attack 10 ms, release 100 ms, hard knee, makeup 0 dB. They are not a measured microphone and not an Easy Effects preset. `CompWriter` is the only producer. It is not `Clone` and not `Sync`, and publishing takes `&mut self`. `CompReader` holds the consumer index, one per channel. It is not `Clone` and not `Sync`, and `StripMixer::process` takes `&mut CompReader`, so two mixers cannot share one reader. The loop thread builds the detector coefficients and publishes the block by swapping an index in a triple buffer. `process` holds that reader and only loads the block. It does not build coefficients, allocate, or lock. A new block is linearly ramped across 256 samples, including when the quantum is shorter, and the last sample of that ramp uses the new parameters. A block built at another sample rate is left unused, except a bypass block: wet is 0, so the samples stay unchanged, and the follower still steps with that block's attack and release until the loop thread republishes at the callback rate. Gain reduction for each strip and the master is one atomic, in dB. It is the minimum of the curve over the block, so a short transient is kept when a later sample has already released. It is 0 when every sample in the block is bypassed or under the knee. Makeup is not part of that number. `block_cost_is_measured` in the compressor module times one settled 256-frame stereo block (strip and master) and prints `MEASURED compressor block:` with the duration, the profile, and `OMAMIX_MACHINE`. It does not fail on a time bound. The number is whichever machine ran the test. It is not an XPS measurement and not a latency budget. The master limiter runs in `StripMixer::process` after the master compressor and before this function returns. The filter applies the optional 440 Hz tone and the master fader after that, so those are not limited. It is a stereo-linked lookahead true-peak limiter. The detector is the same 4× windowed-sinc interpolator libebur128 uses for true peak (49 taps, Hann window, factor 4), and it also takes the raw absolute sample so a sample peak cannot hide between the oversampled points. Lookahead is a parameter from 0 to 20 ms. The default is 5 ms. The master starts on at ceiling −1 dBTP. `0` ms is a clipper: the delay is off, and each output sample is held to the guarded ceiling. A fixed guard of 0.30 dB ([`LIMIT_GUARD_DB`](../crates/omamix-core/src/limit.rs)) sits under the published ceiling inside the gain computer. The attack span is half of the lookahead after the 6-sample detector delay, and at least 1 sample. At 0 ms that span is 1. Release is a fixed 100 ms one-pole, not a control. `LimitWriter` is the only producer. It is not `Clone` and not `Sync`, and publishing takes `&mut self`. `LimitReader` holds the consumer index. It is not `Clone` and not `Sync`, and `StripMixer::process` takes `&mut LimitReader`. The callback loads the block. It does not build the interpolator or the clip plan, allocate, or lock. `LimitRuntime::new` builds the clip plan off the audio thread. `callback_quantum` has one production writer: [`LimitReader::note_callback_quantum`](../crates/omamix-core/src/limit.rs) on the audio callback. Wet snaps when a block is adopted. Ceiling and release ramp across 256 samples, not across the quantum. A lookahead change crossfades to the new delay over those same 256 samples. The sliding minimum is a preallocated monotonic deque. `MinDeque::note_order` does not panic. A backward detector clock latches a fault in test and debug builds. Reported latency is the delay in the master: 0 when the master is bypassed or lookahead is 0, otherwise [`lookahead_samples`](../crates/omamix-core/src/limit.rs) at the callback's rate. The loop thread copies that number into `ProcessLatency` as samples, with `ns` 0 and `quantum` 0, because PipeWire adds those fields. Output port `Latency` is the upstream peer's maximum rate (`upstream_rate`) plus that delay. The filter main loop stores and reads that rate. The audio callback does not read it. Input port `Latency` is the delay alone. Peer `ns` and quantum are not stored. `node.latency` is not set. The graph clock chooses the rate and the quantum, and this delay is `ProcessLatency` in samples at that rate. A 0 ms request is stored as 5 ms when [`zero_ms_limiter_cap`](../crates/omamix-core/src/limit.rs) is 0. That cap scales `ZERO_MS_CAP_48K_256` (27) by quantum and rate, so a 256-frame block at 48 kHz still allows the clipper and a 1-frame block at 48 kHz does not. The loop thread logs one line, and the master keeps a flag until an explicit lookahead, a reset, or a disable. A longer quantum does not put that master back on 0 ms. The `DspChain` template still lists five identity placeholders in spec order. Noise reduction is not implemented, and neither is a per-strip limiter. The live high-pass, graphic EQ, compressor, and master limiter are the mixer path above, not those placeholders. Claiming a tap slot publishes a flat EQ block and a bypassed compressor on the loop thread. Freeing publishes those blocks on the loop thread as well, then the data loop clears EQ filter memory and the compressor envelope with the smoother reset. The data loop does not design coefficients. The consumer index of each triple buffer is not reset, so a reused slot does not alias a buffer the producer still owns. `block_cost_is_measured` in the EQ module times one settled 256-frame stereo block (high-pass plus ten peaking sections, strip and master) and prints `MEASURED eq block:` and the duration. It does not fail on a time bound. That number is also whichever machine ran the test. It is not an XPS measurement and not a latency budget.

A PipeWire `filter-chain` module, or a general LV2 host, was the other option:

- `libpipewire-module-filter-chain.so` is on disk, and SPA filter-graph plugins exist for builtin, ebur128, ladspa, lv2, and sofa. None of those modules were loaded in the daemon during the baseline.
- Loading filter-chain is a server module. Dynamic strips mean rebuilding that graph, and a crash can leave it resident. That is the same teardown class as `module-remap-source`.
- lilv 0.28.0 and LV2 1.18.10 **specs** are installed. There are no LSP, LADSPA, or DeepFilterNet plugin binaries on this machine. A filter-chain or LV2 host would have nothing useful to instantiate for the v1 effects.
- `rnnoise` 0.2 is installed as a C library (`/usr/include/rnnoise.h`, `-lrnnoise`). Noise reduction should call that library from a `DspStage` later, in-process.
- `libebur128` 1.2.6 is installed. The loudness meter can wrap it later. The scaffold does not link it yet.

When Tim installs LSP or an LV2 noise plugin, a stage can host it through lilv without changing the graph model. That dependency is not in the scaffold.

## Real-time thread

The PipeWire main loop runs on its own thread (`omamix-pw`). That thread owns the context, the core, the registry, the filter, and any monitor stream. PipeWire's `Rc` handles are not `Send`, so they are not shared with the control thread.

The control thread sends `Shutdown`, a master-fader, a monitor flag, `SetStripParam`, an EQ update, a compressor update, or a master-limiter update through `pipewire::channel`. That write wakes the loop. The callback runs on the loop thread and applies the message. A timer on the same thread drains `CommandQueue`, which is what `CommandSender::submit` fills. `process()` does not receive on either channel. It writes the master `AtomicMeter`, each strip meter (one peak and RMS snapshot), each gain-reduction atomic, the scope rings, and the `MixSlot`, and it reads `AtomicParams`, `StripParamBank`, the published EQ coefficients through `&mut EqReader`, the published compressor block through `&mut CompReader`, and the published limiter block through `&mut LimitReader`. It also stores the sample rate it just used. The loop timer rebuilds EQ, compressor, and limiter coefficients when that rate is not the one they were built at. A limiter block from another rate is still applied: the callback recomputes the delay and the release coefficient at the rate it is running, so the master does not pass unlimited audio before the loop republishes. Hold and decay are not in that callback. Strip smoothing state, EQ filter memory, the compressor envelope, and the limiter delay stay on the data loop. The master gain in `AtomicParams` starts at unity: there is no built-in mic boost, and the value is not taken from any one machine's speech level. `NullEngine::drive` is the same drain, and it is what tests call. A window built with `--features pipewire` starts the PipeWire thread and sends scene changes on that queue. A window without the feature still holds a `NullEngine`. `omamix --headless --mix-mic` starts the same thread.

`upstream_rate` is the max of the per-port upstream rates (`upstream_fl` and `upstream_fr`). The filter main loop stores it in `recompute_upstream` (`on_param_changed` calls `note_peer_latency`) and reads it in `write_known_port_latency`. The audio callback does not read it.

| shared item | writers | readers |
| --- | --- | --- |
| `upstream_fl`, `upstream_fr`, `upstream_rate` | `recompute_upstream` is an atomic load-max-store. `on_param_changed` runs on the filter main loop and calls `note_peer_latency` | loop thread reads `upstream_rate` in `write_known_port_latency` (filter main loop, same thread as `on_param_changed`). The audio callback does not read it |

## Clocking

A capture device's clock and a playback app's clock are not the same device. On one example laptop (XPS15-OMARCHY) the capture device was a USB audio interface; any host may use a built-in mic, another USB device, or something else. A PipeWire link does not resample. Linked nodes join one driver group. The USB mic and each app stream rate-match inside their own nodes and adapters. `process()` does not resample; it sums the quantum it was given.

**Choice: one `pw_filter`, one `process` callback (`ClockPlan::SingleFilter`).** That filter is the internal mix engine. Mix Mic is the adapter it feeds. `PW_FILTER_FLAG_DRIVER` is not set, and neither property bag writes `node.driver` or `node.want-driver`. PipeWire fills the split: the null-audio-sink factory sets `node.driver` on Mix Mic, and the filter gets `node.want-driver` with `node.driver-id` pointing at Mix Mic. `priority.driver` is 1 on both nodes, so Mix Mic loses a driver election against an ALSA device. Capturing Mix Mic clocks the adapter, which clocks the filter. Strip taps are input ports on the filter. A separate `pw_stream` per strip would put each strip on its peer's driver. Mix Mic does not set `node.latency`, so the graph clock chooses the rate and the quantum. The limiter delay is `ProcessLatency` in samples at that rate.

Headphone sends and the monitor are the exception that stays off this clock. Each is its own playback stream. Its `process` copies a slot the filter already wrote. If that stream's driver is the sink, it can repeat or skip a quantum relative to the filter. The monitor copies the master `MixSlot`. A headphone send copies the strip tap, not the master, so the mic is not in the headphones.

## Browser identity and the Mix Mic loop

Chromium tabs and browser studios share `application.name` and `application.process.binary`. A `RouteKey` that only has those two claims every stream of that app, which is why "other desktop" then leaves all of them out: better to miss a tab than to mix it twice. The key also stores `media.name`, pid, and object serial. `matches_stream` uses `media.name` when the key has one, so two tabs can be different strips once the UI writes that down. It does not require pid or object serial; those only split two streams that are live at the same time (`disambiguates_live`).

**Loop guard.** `feeds_mix_mic` returns false when the playback node's `client.id` or pid is [`OwnClient`](../crates/omamix-core/src/route.rs), when `omamix.owned` is set, or when `upstream_includes_mix_mic` walks the link graph and finds Mix Mic upstream of that node. `tap_allowed` with `TapScope::SharedClient` also refuses every stream of a client when any node of that client is Mix Mic or is fed by Mix Mic. That scope is the automatic "other desktop" strip and an application strip whose route key has an empty `media.name`. An application strip whose route key includes `media.name` stays on the per-node walk, so one named tab can stay a strip while another tab of the same client captures Mix Mic. Node globals include `client.id`. Binary, `media.name`, pid, and `omamix.owned` arrive on bind. If a graph is present and the stream has no `node_id`, the walk cannot run and the stream is refused.

## Linking

On `global`, the loop thread records the node. Ports carry `node.id`, `port.id`, `port.direction`, and `audio.channel`. `stereo_output_ports` picks FL/FR, or two unlabeled outputs in `port.id` order, or one unlabeled mono port used for both sides. Link factories take that `port.id`, not the registry global id.

`start_link(false)` stays in `LinkPhase::WaitingForPorts` until the peer's output ports and the filter's `in-<peer>-FL/FR` ports exist. `advance_link` moves Waiting to Linking. The loop thread then calls `link-factory` with `object.linger=false`. Active or paused moves Linking to Linked and clears that tap's try count and wait, the same way a live engine link clears its counters. If the link call fails, `link_failed` goes to `LinkPhase::Failed`. The attempt then retries with a doubling backoff of 1, 2, 4, and 8 ticks of the 50 ms timer, and stops after four failures. Freeing a mixer slot, or a change to that peer's own ports, gives an exhausted failure a new budget of four attempts, at most twice since the last active or paused link. A successful link clears that revival count. A link this process added or removed does not refresh the budget, and neither does another node appearing or disappearing. The line `stopped retrying` is logged once for that peer. A tap that is still inside its backoff keeps that wait. If a link disappears without an error, the tap is unlinked and the same budget decides whether it is tried again. Each time a link that the registry had already shown disappears, a relink count increases. After four, the next wait is at least 16 ticks. A later success clears that count, so the next removal starts again. Reusing a retired filter port instead of freeing it is future hardening: the current path clears the slot on the data loop and then frees the port. `PeerVanished` does not retry. Failure clears `saw_edges`, so a retry is not torn down before the registry shows the new edges. The loop guard runs before any of those retries: a peer whose upstream includes Mix Mic, or a shared client that captures Mix Mic, is dropped rather than linked again. If the peer disappears, `peer_removed` goes to `PeerVanished`, the link proxy is dropped, and a later global for a new node id starts a new attempt. `omamix --headless --mix-mic` with no `--strips` creates the filter, the Mix Mic adapter, and the links from the filter outputs into the adapter. It does not create strip taps. The adapter ports are configured on that node at creation, so they exist without a session manager.
